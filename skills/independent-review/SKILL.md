# Independent Review (`independent-review`)

## 1. Purpose
The `independent-review` skill provides an impartial, adversarial, and uncompromising assessment of code changes. To prevent cognitive bias and complacency, this review is conducted from the perspective of an independent auditor who assumes the code may contain hidden flaws, scope creep, or superficial implementations. It serves as the primary verification engine for **Gate G5 (Independent Review)**.

## 2. When to Use It
Activate this skill whenever:
- Implementation tasks for a milestone or workstream are marked complete in Gate G4.
- An adversarial audit is required on pull requests, branches, or subagent deliverables.
- Verifying strict adherence to requirements without "AI slop" or undocumented feature additions.
- Making the formal determination to approve Gate G5 or reject and loop back to Gate G4.

## 3. Prerequisites
- Implementation is complete with passing test evidence (`contracts/implementation/contract.json` is `VERIFIED`).
- Full Git diff between current branch and baseline commit is accessible.
- Quality contract schema (`core/schemas/quality-contract.schema.json`) is available.

## 4. Inputs
| Input Name | Type | Description |
|---|---|---|
| `targetCommitOrDiff` | `string` | Commit hash, git range (`origin/main...HEAD`), or diff string. |
| `requirementsContract` | `object` | Approved requirements specifications and acceptance criteria. |
| `verificationEvidence` | `object` | Automated test outputs and exit codes collected during G4. |

## 5. Procedure (Step-by-Step)
1. **Full Diff & Scope Integrity Inspection**:
   - Execute `git diff <base_commit> HEAD` across all changed files.
   - For every change, correlate it with an approved item in `contracts/requirements/contract.json`.
   - **Scope Creep Audit**: If files or features were added that are neither in-scope nor architecturally approved, flag them as an unapproved scope expansion violation.

2. **Anti-Slop & Baseline Policy Audit**:
   - Inspect code and commit messages for decorative emoji (BL-001).
   - Search for hardcoded mock data in production classes or database helpers (BL-002).
   - Check for placeholder buttons or stub functions with empty bodies or `TODO` comments (BL-003).
   - Check for blanket exception suppression (`try: ... except: pass`) or unexplained workarounds (BL-004).
   - Check package manifests for unvetted third-party libraries (BL-005).

3. **Adversarial Edge-Case & Threat Inspection**:
   - Probe defensive coding: How does the system respond to `null`, `undefined`, empty strings, negative numbers, or payload strings over 10MB?
   - Check error propagation: Are user-friendly error codes returned instead of exposing internal stack traces?
   - Check race conditions: Are asynchronous or file I/O operations protected against concurrent mutation?

4. **Evidence Audit**:
   - Review execution logs from `testing-and-verification`.
   - Verify that test assertions actually test the new logic rather than vacuously asserting `True == True`.

5. **Defect Triage & Scoring**:
   - Classify findings into:
     - **BLOCKING**: System crashes, data corruption, anti-slop violations, broken contracts, missing error handling.
     - **MAJOR**: Performance regression, missing edge case test, suboptimal type annotations.
     - **MINOR**: Minor style formatting inconsistency, documentation typo.

6. **Review Report Generation & Decision**:
   - Publish findings in `docs/validation/independent-review-report.md`.
   - If any BLOCKING or MAJOR defects exist:
     - Set status to `REJECTED` in `contracts/quality/contract.json`.
     - Trigger lifecycle transition from G5 back to G4 (`REVIEW_DEFECTS_FOUND`).
   - If zero BLOCKING/MAJOR defects remain:
     - Set status to `APPROVED` in `contracts/quality/contract.json`.
     - Authorize transition to Gate G6 (`G5_PASSED`).

## 6. Expected Outputs
- `docs/validation/independent-review-report.md`: Formal audit report with findings and severity triage.
- `contracts/quality/contract.json`: Signed-off quality contract.
- Backlog entries in `memory/state.json` for any minor non-blocking issues.

## 7. Applicable Approval Gates (G0-G6)
- **Gate G5 (Independent Review)**: Exclusive gate governing this skill. Approval unlocks Gate G6.

## 8. Failure and Recovery Behavior
- **Review Rejection**: When review fails, compile an actionable remediation list with file paths and line numbers. The orchestrator returns the task to `controlled-implementation` for correction.
- **Flaky Tests Uncovered**: Quarantine flaky test, file a defect in `backlogAndHistory.bugs`, and require deterministic fix before G5 sign-off.

## 9. Verification Criteria
- Zero BLOCKING defects remain open in the review report.
- Zero anti-slop baseline violations exist in the reviewed diff.
- Reviewer findings provide exact file paths and verifiable rationale.
- Gate G5 transition adheres to the deterministic lifecycle FSM.

## 11. Review Findings Standard

Applies to every finding this skill reports.

- **Read beyond the diff.** Read the callers and callees of each changed function. When a signature, return value or behaviour changes, find every caller.
- **Judge against the real load.** Find the expected load in the repository (one person running a script, or many users and processes) and say which one you assumed.
- **Concrete case or no finding.** Each finding names the input or situation that produces the wrong result. Re-read the lines to confirm the caller exists or the value can really be empty.
- **Order:** correct, safe, holds under load, tested where risky, fast, lean.
- **Format:** number findings across three groups (must fix, should fix, nice to have). Each has a location (`file:line`), what the code does, the problem, the smallest fix, and the cost of skipping it.
- **Finish with a verdict:** `Ship`, or which findings to fix first, plus `Not checked:` for anything that mattered but could not be verified.
- **No style taste and no vague "consider".** A shortcut whose limit is documented in a comment is a decision, not a finding, unless the expected load already crosses it.
